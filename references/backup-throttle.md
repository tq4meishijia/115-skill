# 115 开放平台限频事实与恢复状态机（人工维护）

> **通篇为社区实测 / 开源实现反推 / 工程假设，不是官方公布值。**
> 115 官方开发者协议 5.10 条只声明「会单方面制定及实施服务使用限制措施，
> 包括可能发出的请求数量限制」，**未公开任何 QPS / 每分钟 / 每日数值**，
> 也未定义 HTTP 429 或 `Retry-After`。本文数值需人工随实测更新。

## 1. 事实基线（含置信度）

| 事实 | 来源性质 | 置信度 | 对设计的影响 |
|---|---|---|---|
| 官方协议 5.10 声明会限制请求数量，但无数值 | 官方协议条文 | 高 | 禁止把 2 QPS 写成官方值；必须有兜底 |
| 创建应用需填「预计每日调用次数」 | 官方流程 | 中 | 可能存在日配额，需压总请求量 |
| 限流主要表现为业务码 `770004 访问频率过高`、`406 已达到当前访问上限`，**而非 HTTP 429** | 开源实现 + 官方社区实测帖 | 中—高 | 只防 429 会漏；现有 `client.py` 只认 429 是已知缺口 |
| 触发后封控可达 **2–4 天**；有实测冷却 > 120 s / 约 5 分钟恢复 | 社区实测 | 中 | 触发即长冷却 + 熔断，不重试轰炸 |
| OpenList 115 驱动 `LimitRate` 默认 **1 次/秒**，PageSize 200 | 开源源码 | 高 | 与用户「实现 ≤ 1 QPS」互相印证 |
| 同路径重名写入返回 404 | 社区实测 | 中 | 幂等需版本化命名 |
| `status=6/7/8` 是防伪造秒传的二次校验，**不是频控码** | 官方上传文档 | 高 | 不得误判为限流 |

> 用户设定的「平台 2 QPS」是工程假设；本功能**实际 ≤ 1 QPS**。
> 官方协议禁止「分布式请求、代理服务器集群、自动化脚本破解」等行为。
> 实现约束：全部请求走**单客户端串行通道**；禁止多账号、代理池、伪装请求来源；
> 禁止拆分请求来源或隐藏调用来源的实现。提速只允许通过「减少合法请求次数」
> （状态跳过 / 秒传 / 聚合）实现。

来源（供人工复核）：`https://open.115.com/`、`https://www.yuque.com/115yun/open`、
OpenList `drivers/115_open/meta.go`、qmediasync `internal/v115open/constants.go`、
115 官方社区反馈帖。

## 2. 可重试 / 不可重试分类

| 类别 | 具体 | 处置 |
|---|---|---|
| L1 可重试（复用 `client.py`） | 网络异常、HTTP 500/502/503/504、HTTP 429 | strict 档 3 次，`min(2**attempt, 8)` + 0–0.5 s 抖动，`Retry-After` 封顶 30 s；每次重试仍经同一节拍器 |
| 业务频控（governor 补识别） | 业务码 770004 / 406 | **立即停止本轮业务请求** → COOLDOWN → PROBE → RAMP；冷却期内重试次数 = 0 |
| 授权失效 | `AuthError` / 401 系 | `auth_required` 事件 + 退出 2 + 告警；重试次数 = 0，禁止自动重授权/扫码 |
| 确定性错误 | 404 同路径重名、参数错误 | 不重试；版本化改名重排一次或记终态 |
| 未知码（灰区） | 未列入码表的 code / errno | 只出 `UNKNOWN_WARNING` 候选信号，不自动进 COOLDOWN；是否新增为频控码由人 / QA 裁决 |

## 3. 恢复状态机（可判定）

状态：`RUNNING` → `COOLDOWN` → `PROBE` → `RAMP` → `RUNNING`（恢复）或 `TRIPPED`（熔断）。

| 当前 | 事件 | 下一状态 | 动作 |
|---|---|---|---|
| RUNNING | HTTP 429 或业务码 770004/406 | COOLDOWN | 立即停本轮业务请求；冷却 300 s 起；`Retry-After` 只作地板 |
| COOLDOWN | 冷却到期 | PROBE | 以 0.5 QPS 发**单发**探测（每轮 1 个请求） |
| PROBE | 连续 5 轮单发全成功 | RAMP | 逐档提速 |
| PROBE | 任一轮失败 | COOLDOWN | 冷却翻倍；连续失败轮 +1 |
| COOLDOWN | 连续失败轮 ≥ 3 | TRIPPED | 落状态 + 告警 + 退出 3，等下一调度周期 |
| RAMP | 4 档走完且无频控事件 | RUNNING | 冷却基数重置 300 s、失败轮清零 |

| 参数 | 默认值 |
|---|---|
| 冷却序列 | 300 → 600 → 1200 → 2400 → 3600（封顶） |
| 探测 | 0.5 QPS / 2000 ms / **单发** × 5 轮；轻量端点 `GET /open/user/info` |
| 恢复判定 | 连续 5 轮单发全部 HTTP 200 且业务 `state=true` 且无 770004/406 |
| RAMP 档位 | `[0.5, 0.7, 0.9, 1.0]`，每档观察 ≥20 请求且 ≥60 s 无频控事件才升档 |
| 硬上限 | **1.0 QPS，永不升到 2 QPS** |
| 熔断阈值 | 连续 3 轮探测失败 |

**冷却期内 0 次重试**；探测请求本身是 `/open/` 请求，计入 `N_api` 且必须守 G1
（0.5 QPS / 2000 ms 单发，仍在 ≤ 1 QPS 内）；恢复后速率不得高于 1.0 QPS。

## 4. 为什么不改 `client.py`

现有 `client.py` 的 `RETRYABLE_HTTP=(429,500,502,503,504)`、3 次退避、
`Retry-After` 封顶 30 s、401 自动刷新重放都已具备。备份在**不改源码**前提下：

1. 把 `client._limiter` 换成 `backup.pacing.Pacer`（继承 `TokenBucket`、只覆盖 `acquire`），
   使 L1 重试、token 刷新回放、二次校验重发全部经同一节拍器；
2. 用 `client.on_request / on_retry` 钩子精确统计 `N_api` 并写事件；
3. 在 governor 层捕获 `APIError`，按业务码补识别 770004/406 并驱动 FSM；
4. `config.rate_limit` 强制覆盖为 1.0，`PAN115_RATE_LIMIT=1` 显式生效。

**遗留风险**：其他子命令仍不识别 770004/406。若需全 skill 统一治理，后续扩展
`client.py` 的频控识别并重跑验收（本次不改源码）。

## 5. 验收纪律

- 全部频控 / 退避 / 恢复验证使用**离线故障注入**（`backup selftest` 的 FakeClient 与
  可注入 sleeper），**禁止在真实 115 账号制造 429 / 770004 / 406**。
- 正常场景合格线：HTTP 429 = 0、770004 = 0、406 = 0；`peak_qps ≤ 1.0`；
  平均相邻请求间隔 ∈ [1.0, 1.2] s。
